## Blockers

- **[critical] data-integrity**: Public grading waits on the edge. Every result the site shows comes from engine PR 10: the dashboard's "Results per window ... Engine PR 10" and "Track record ... Engine PR 10" rows (What the dashboard reads), engine F "Outcome updates. From PR 10", and the notification plan's "Updates ... from engine PR 10". PR 10 waits for Chris to read the report, and "if nothing beats the placebo after costs, we stop and rethink" (engine, Gates). D3 "shares the engine's evidence gate" (Build order). So from the cutover until PR 10, and for good if there is no edge, no live call is graded anywhere. That breaks the growth plan's premise ("graded in public, misses included"; "the public record starts that day" at the soft launch) and leaves the Track record page with nothing to show. Grading a live call needs bars and arithmetic, not an edge. (Skeptic; the Contrarian's Blocker rests on the same dependency.)
  - **Recommendation:** Split engine PR 10. Move live-alert outcomes (move at each window against the benchmark after costs, hit or miss, written as alert revisions) into PR 6 or a small PR at the cutover, with no edge gate. Split D3: the Track record page and per-signal results ship when grading ships, at or right after the cutover; only Evidence/report, tiers and typical moves wait for PR 10 and an edge. Send this change to the engine and notification planners as well.

- **[critical] security**: D1 as written publishes licensed raw prices on day one, against the agreed 1 Oct rule. D1 adds /api/v1/bars/<symbol> over market_bars and a "1-minute prices since the post" chart (Signal page item 4; D1 row). The 00:05 note adds /api/v1/prices/latest, polled every 5 s. The Evidence drill-down lists an "entry price". The signal page "renders the stored alert as is", and engine PR 10's outcome revisions carry "the entry price and time used" inside alert.v1 (engine F). The notes agree that public output shows computed moves only, with no raw entry price (ui-plan-hookups, growth "Prices"), but the doc's endpoint list and D1 were never changed. Breaking this risks more than the site: Alpaca is the engine's only minute-bar source for backtests, so losing the account would take down the evidence engine. Two more problems. Withholding the entry price does not stop anyone rebuilding the prices, since any free quote for one minute plus a 1-minute % series gives the whole series back; the real question is whether Alpaca's terms treat derived % series as its data (unverified here). And the doc's "minute bars cover every post since 2022" is wrong for the site: the database keeps 1-minute bars only for alert windows and the last 30 days, with research history kept as files (engine Data model, storage tiers).
  - **Recommendation:** Drop /api/v1/bars and /api/v1/prices/latest as public endpoints. The public API serves only alert_progress's computed move against the benchmark (updated each minute) and the per-window results. Alert.v1 never carries the entry price: the engine keeps it in an internal column. Before D1, get Alpaca's position in writing (or read the terms off-sandbox) on whether publishing % moves derived from its data is allowed. Until then the chart is a handful of points (the move at each window), not a minute series. Historical pages show window results only.

## Risks

- **[major] performance**: Launch-day traffic will rate-limit everyone at once. api/rate_limit.py:10 keys on slowapi `get_ipaddr`, which looks up the header "X_FORWARDED_FOR" (underscores; checked in the installed slowapi) and never matches the real X-Forwarded-For. It falls back to request.client.host, which is Railway's proxy, because uvicorn starts without proxy-header trust (railway.json:78). So every visitor shares one bucket. The plan's "rate-limited per address" (What the dashboard reads) is false as the code stands. Each visible tab makes 12 polls a minute, into one replica (railway.json:8) running one uvicorn process. The plan says the load is "inference, not measured". At the growth plan's public launch, the likely failure is a site-wide 429 and a grey header dot. A further contract hole: unless the /alerts list returns the head seq read in the same transaction, a fresh page either misses changes or polls after=0 and replays the whole history.
  - **Recommendation:** In the first /api/v1 PR: key the limiter on the real client IP (uvicorn --proxy-headers with Railway's proxy range; verify Railway's forwarding header before D1) and size limits for NAT'd crowds; return `head_seq` with list responses; keep the newest seq in memory so empty polls skip the database; send `Cache-Control: public, max-age=5` on changes, evidence and record responses; poll every 15 s, not 5 (Telegram is the push surface). Load-test 200 requests a second before the public launch.

- **[major] architecture**: The cutover is coupled to the largest dashboard PR, and the dashboard has no rollback. The web service's first contact with the engine database is the cutover sitting ("At the cutover you give the web service a read-only connection string", Build order). Yet N2 must merge before the cutover and needs that variable. If new code builds its DB engine at import, N2's merge takes today's site down. D1 deletes today's frontend, so the engine's rollback ("switch the old workers back on", engine G) has no site to return to without a revert, and every revert redeploys all 12 services. The cutover sitting already stacks PR 8, the subscriber step, the webhook switch, the variable, the domain (growth, Launch step 3), D1 and the worker switch-off. The only real-data check for D1 is optional.
  - **Recommendation:** Set WEB_DATABASE_URL at engine PR 7, when Chris creates the engine database anyway. Run N2 and D1's endpoints on the real web service against the shadow week's data. Make the web app boot without the variable (lazy DB engine). Drop "the cutover waits for D1" and merge D1 in its own sitting; a stale old site for a few days is an acceptable fallback. State D1's rollback (revert) in the plan.

- **[major] scope**: Cut D2, the public Status page and /api/v1/status/engine. It duplicates the engine's `python -m engine status`, health endpoint, daily status and operator messages (engine A). Publishing "each mirror's last poll ... how often each was first" (Status) and "first seen and by which feed" (Signal page item 5) tells everyone that the product resells CNN's feed and trumpstruth.org, whose reuse terms the growth plan already doubts (CNN live-feed terms bar commercial use, unverified). Meanwhile nothing watches the public site itself.
  - **Recommendation:** Delete D2. Also drop N2's /api/v1/status/outlets and N4's engine_status tool, which exist only for that page. Keep the header freshness dot (one "last post seen" field on an existing response) and one public line on the Record page, "median post-to-alert time this week", without naming feeds. Add an engine scheduler job that checks the web's /api/health every minute and calls notify_operator after 3 failures.

- **[major] scope**: After growth's changes the site has about 10 pages: Live, Signal, Evidence, Track record, Status and Connect, plus ticker, topic, report and methodology/disclaimer. Several overlap. Evidence is the backtest report. A ticker page is the natural drill-down of an Evidence row, which makes /api/v1/evidence/<topic>/<ticker> redundant. Topic pages repeat a filter. Connect (D4) is a list of links. The Evidence page also invites misreading: "rows sort strongest first", green or red in every cell, and three evidence layers behind a switch, when most topic, ticker and window cells have fewer than 20 cases.
  - **Recommendation:** Six pages in three PRs. Home; signal; ticker (/t/<slug>, which is also the Evidence drill-down); Record (the live track record); Report (Evidence and the backtest report as one page); About (methodology, disclaimer and the Connect links). Drop D4, topic pages (keep topic as a filter) and the layer switch (show the alerting layer and the live record; the others go in the downloadable report). Show cells with 20 or more cases by default and colour only those that pass Benjamini-Hochberg.

- **[major] scope**: "All posts" and the 36,580 historical posts. The "All posts" filter on the live list is the only consumer of a second cursor (signals.seq, an engine table column) and its merge logic. It also turns every Trump post into a public full-text page, against growth's rule "we quote a line and link to the original". Pre-cutover pages "show their call" from a backtest layer (keyword rules, LLM backfill, or the old ensemble's record with its known bugs #217 and #218) with no label, which breaks growth's rule that backtest and live numbers are always labelled.
  - **Recommendation:** Remove "All posts" from the live list, and have the engine drop signals.seq unless another reader needs it. Pages for posts with no call, and for pre-cutover posts, are noindex and left out of the sitemap, show an excerpt and a link, and say which layer made the call and that it was never alerted.

- **[major] scope**: The site is built as a live terminal when its job is the record and turning visitors into followers. The Summary frames it as "show it within seconds", and the home page is a live list with a laptop split view, a "new" bar, a tab-title counter and infinite scroll. That machinery serves 2 to 5 sent alerts a day (notification plan, Costs) that already arrive by Telegram push. The growth plan's cold visitors from X, Reddit and HN get no pitch, no record and no follow path on the home page.
  - **Recommendation:** Make the home page the pitch line, the graded record summary, the latest calls (updating quietly) and the follow buttons with ?ref. Drop the split view, the "new" bar and the tab counter, and replace infinite scroll with an "older" button.

- **[major] data-integrity**: The headline "how much of the typical move is left", and the signal page's question "is it still worth trading?", are statistically unsound and the riskiest wording in the project. The typical move minus the move so far is not the expected remaining move: once a stock has moved, the rest of its move follows a different distribution (overshoot or reversal), and the backtest does not estimate that. Timing language about one security at one moment is also the condition the growth plan says strains the publisher exclusion (Legal and data rules; unverified there). This is the plan's chosen headline (Decisions, "Headline on each alert").
  - **Recommendation:** Headline the call, the move since the post against the benchmark (with its as-of time), and how similar past posts moved at each window, with n and tier. Remove "left" and "still worth trading" from the copy and the decisions table.

- **[major] compatibility**: The doc models stocks only and contradicts the engine's crypto default. "Result windows: 5 min ... 1, 3 and 5 days, against SPY" is marked Approved. The header carries a stock-market clock, Track record is measured "against SPY", and Evidence has "one column per window". The engine's crypto default uses 5m/15m/1h/4h/24h/3d/7d against BTC, around the clock, with market_open set per alert (engine E and F; notification note). The cumulative Track record chart ("following every sent alert, one line per tier") also never says which window or how overlapping positions combine.
  - **Recommendation:** Take windows and benchmark per instrument from the API and never hard-code them. Split Evidence and Track record by asset class. Base the verdict on alert.market_open, not the header clock. Define the cumulative chart: one window per asset class (close for stocks, 24h for crypto), equal weight, a sum of abnormal returns. Build all of this so it works whichever way Chris decides on crypto.

- **[major] architecture**: The rendering model and the URL scheme have to be fixed before D1, and the approved stack predates them. Growth adds server-rendered titles and preview images for five page types, canonical links, a sitemap and search-led ticker pages. Today's catch-all returns the same index.html for every path (api/main.py:81-95), so no page has its own meta. Two ids compete for one page: notifications deep-links /s/<signal_id> ('truth_social:<id>', with a colon), while the engine adds alerts.public_id "for share links". Links in Telegram posts are permanent from the cutover, and the domain moves at the cutover (growth, Launch step 3). Dynamic preview images earn little: our own X posts carry no links (notification Costs: a link costs $0.20).
  - **Recommendation:** Choose before D1. Either keep the SPA with a catch-all that serves per-URL title, description, canonical link and one static preview image per page type, or go server-rendered (counter-plan). Defer generated images until ?ref counts show people sharing. Pick one permanent URL per signal that works for posts without alerts. Have the domain live before the first channel post.

The endpoints are to use the engine's SQLAlchemy models (What the dashboard reads). The engine has its own package and dependencies, though, and the web service runs `uvicorn api.main:app` from the old tree with no CI at all (.github/workflows does not exist). N4's MCP tools "use the same queries" as D3, but N4 is sequenced only after engine PR 10, not after D3. Also, api/dependencies.py:7 imports shit.db.sync_session, which opens a pool to the old production database at import (shit/db/sync_session.py:14-38), and D1 does not list it for deletion.
  - **Recommendation:** Put /api/v1 in the engine package (for example engine/api, imported by the web service) or give it its own CI job on the engine's test Postgres. Name one owner for the conventions, set in whichever of D1 and N2 lands first. Sequence N4 after D3. Have D1 delete api/dependencies.py, and add a test asserting api/ imports nothing from shit/ except routers/telegram.py until PR 11.
