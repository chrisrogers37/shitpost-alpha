## Blockers

- **[critical] scope**: D1 is the only PR on the cutover's critical path and it carries the whole product. As written it holds the new stack (React, TypeScript, Vite, TanStack Query, lightweight-charts, CSS modules, Vitest, Playwright, a CI job), the live list (Sent / All alerts / All posts filters plus a ticker filter, a "new" bar, tab-title count, market clock, health dot, infinite scroll, laptop split view), a seven-section signal page, `/api/v1/signals`, `/api/v1/bars`, link previews, and the deletion of the old site. Growth's change list then adds ten more items to this plan (own domain with canonical links and sitemap, server-rendered cards for five page types, ticker, topic and report pages, Telegram receipt links, follow buttons with ?ref tags, visit counts, a methodology page, % charts, a README rewrite) under the rule that each "should fit inside a PR the plan already has". Most cannot. What this holds hostage is mission goal 4, alerts reaching subscribers: the cutover waits on D1 only because the old site reads the old database. The plan gives no S/M/L size for any PR, so D1's weight is invisible.
  - **Recommendation:** Name D1 as "the cutover minimum" and cut it to what the soft launch needs: signal page (verdict, post as a quoted line plus link, calls, % chart, timing, folded reasoning), a plain alert list with Sent and All alerts and the 5-second poll, `/api/v1/signals` plus the % path endpoint (see the raw-price finding), the methodology and disclaimer page, follow buttons, the own domain with canonical links, one share card for `/s/<id>`, and the old-frontend deletion. Move the split view, tab counter, market clock, ticker filter, infinite scroll and the All posts filter to a later PR that is allowed to slip. Assign every other growth item to a named PR by launch phase (cutover, public launch, post-launch) and put an S/M/L on each. If D1 still sizes as XL, split it so the signal page and its endpoints land first; the shadow week's alerts already link to `/s/<signal_id>`, so that page is needed by PR 7 anyway.

- **[major] compatibility**: D1 as written publishes raw prices and entry prices that growth and the engine have agreed never go public before Alpaca's consent or a licensed feed. The conflicts: `/api/v1/bars/<symbol>` and the signal page's "1-minute prices since the post" chart; the Evidence drill-down that lists "entry price" per post; the 1 Oct hookup note adding `/api/v1/prices/latest` polled every 5 s on an open signal page; and the engine's outcome revisions that "carry the entry price and time used" into alerts the public API serves. A % series plus one entry price rebuilds the raw prices, so any one of these defeats the rule. D1's own verification (5-second browser test, screenshots) would pass while the money plan's licensed-prices precondition is already breached from the soft launch.
  - **Recommendation:** Replace `/bars/<symbol>` with a server-computed `/api/v1/signals/<id>/path` that returns % since the post for the ticker and its benchmark, built from `alert_progress` and the bars, so no raw price leaves the server. Drop `/prices/latest` and the entry-price column and field from every public page. Ask the engine and notification planners to keep entry price and time out of the public alert JSON and alerts API (internal tables only). Add a D1 test that fails if any public `/api/v1` response contains a raw price field.

## Risks

- **[major] scope**: Effort is weighted to the speed story that growth has dropped. The plan's headline is "show it within seconds" and its home page is a live trading list. Growth's thesis is "we can't win on speed, we win on evidence", with the record as the marketing. But the evidence-bearing parts (tier, typical move left, per-window results, Track record, Evidence) arrive in D3, after engine PR 10 and Chris reading the report. Until then the signal page "shows the model's call alone", so its headline question, "is it still worth trading?", cannot be answered at the soft launch, which is when the first followers arrive. The live-only Track record (alerts only, graded against SPY, misses kept) is the page growth says is the marketing, and it is gated behind the backtest edge although it needs only `alerts`, `alert_revisions` and `alert_progress`; the backtest supplies only the random-time line and the tier promise. Growth also says "the public record starts that day" at cutover, with no page to show it. The two plans disagree.
  - **Recommendation:** Build a first Track record from live data (alerts since the cutover, move against SPY at each window as it matures, misses included) in the first public set, and add the random-time line and tier columns when PR 10 lands. Make the top of `/` the record headline above the list. Keep the Evidence page at D3. If Chris wants no public record before the gate, change growth's "record starts at cutover" claim instead; do not leave the two stories side by side.

- **[major] scope**: The share cards are the one growth item that is truly mission-critical (shared links are the loop) and the least sized. The plan is an SPA served as static files, "no services"; growth demands server-rendered titles and preview images for signal, ticker, topic, record and report pages. Link-preview crawlers behind Telegram, X and Reddit do not run JavaScript, so this needs per-route HTML meta injection in the web service and an image generator (fonts, layout, caching, load on the same service). That is a new moving part hidden inside D1.
  - **Recommendation:** Make it its own named PR ahead of the public launch. Start with `/s/<id>` only: inject title, description, canonical and og tags into `index.html` from the alert row, and render one fixed-template card per alert revision, cached (or ship text-only cards first and add the image later). Add the other page types' cards only when those pages exist. If ticker pages survive (see the D3 finding), decide deliberately whether FastAPI templates beat an SPA for a read-mostly public site; do not inherit the SPA by default now that the original reason ("chosen for the live list") is demoted. Verify by fetching `/s/<id>` as Twitterbot and TelegramBot and asserting the tags and an image that returns 200.

- **[major] scope**: D2 publishes operator tooling as a product page. The engine already has `python -m engine status`, a health endpoint, `job_runs` and operator DMs; the notification plan adds `/api/v1/status/outlets` and an MCP `engine_status` tool; D2 adds a page and `/api/v1/status/engine`. That is four surfaces for facts one person reads. "How often each mirror was first" and each mirror's last poll publicly name the scraped sources, just when growth says CNN's live-feed terms bar commercial use and Truth Social allows only personal use (both unverified) and a lawyer's review is the money gate. No follower is converted by a job's last-run time.
  - **Recommendation:** Delete D2. Keep the header dot (one boolean from a tiny health call) and publish one honest latency stat, median and 95th percentile post-to-alert over the last 7 days, on the Track record page, since a speed claim belongs in a credible record. Leave feed and job detail in the CLI and health endpoint. If a Status page is wanted later, read it from the engine's health endpoint rather than a public `/api/v1` contract.

- **[major] scope**: D3 and the growth additions build the same backtest data four times before there is data to fill them: the Evidence explorer (topic by ticker by window grid, three filters, drill-down, a three-layer switch), growth's report page, ticker pages and topic pages, plus Track record's tier table and one cumulative line per tier. All are views of `backtest_summary` and `backtest_rows`. At a few alerts a day (the notification plan budgets 2 to 5 X-worthy alerts daily) per-tier live lines and a "do tiers hold" table are noise for weeks; growth's own gate asks for 8 or more weeks live. Ticker and topic pages exist for search discovery, but growth's channel table lists no search channel, a new domain will not rank for months, a client-rendered SPA is a poor search surface, and a ticker with a handful of cases is a thin page. The layer switch invites the pooling the evidence rule forbids. Crypto windows (5 minutes to 7 days) differ from stock windows, so one window-per-column table needs two shapes, and crypto is not yet approved.
  - **Recommendation:** Cut D3 to Track record (one line against SPY plus the random-time line, a tier table without per-tier lines), one Evidence table over the layers the evidence rule counts, and the report page as a frozen export from the engine. Cut topic pages and the layer switch. Build ticker pages later, sharing the Evidence table's component, and list only tickers at or above the engine's 20-case threshold (noindex the rest). Do not build crypto columns until Chris approves crypto on the engine card; read the window set from the API per asset class so adding crypto later is data, not UI work.

- **[major] scope**: The plan, together with growth's sitemap, turns the site into an indexed mirror of Trump's feed. The All posts filter, signal pages for posts with no call ("shows the post and why there is none"), full post text on every signal page, pre-cutover posts with pages, and a sitemap cover all 36,580 imported posts. That cuts against growth's rule "we never sell Trump's posts, we quote a line and link" and its flagged terms exposure, for no mission gain: a post with no call has nothing to grade and no analysis to sell.
  - **Recommendation:** Give public pages only to signals that carry a call. Quote at most about 280 characters with a link to the original, on pages and in the public API. Drop All posts from the UI, and keep no-call and pre-cutover signals out of the sitemap and marked noindex. Add "is quoting a post under 280 characters acceptable?" to the list for the lawyer at the gate.

## Gaps

- **[major] scope**: No PR is built for a stranger deciding to follow, and nothing in D1 to D4 verifies one. The home page is a list with no "what is this" line and no follow button. Follow buttons, ?ref tags and the methodology page exist only as growth items with no PR. Connect, the only page that says how to follow, is D4 and waits on N3 (webhooks) and N4 (MCP), the agent audience, which growth ranks fourth, so the Telegram and X links arrive last. Verification is UI behaviour (a row within 5 s, screenshots, links resolve); all four PRs could pass with no measurable conversion. Visit counts are an unverified Cloudflare tool, no PR checks that ?ref values land anywhere, and the follower gate (2,000) needs a funnel someone can read.
  - **Recommendation:** Put the one-line promise ("Every Trump post that moves markets: called in minutes, graded in public"), the record headline and the Telegram and X follow buttons with ?ref tags in the shell of every page from D1. Split D4: Telegram and X follow links ship in D1, the agent links ship with N3 and N4, and drop D4 as a PR. Add acceptance checks tied to the funnel: a test visit's ?ref appears in the visit counts, share cards render for the bot user agents, and each outlet's named Telegram invite link resolves.

- **[minor] scope**: The free, live, public list can contradict the paid-first branch of the money plan. Growth says that if the edge is within about 15 minutes, paid members get alerts first and public outlets wait via a per-destination delay. The dashboard polls the public `/api/v1/alerts/changes` every 5 s with no delay concept and states it "shows nothing the API does not". The risk row "Public evidence shows everyone the edge: your call in the decisions table" points to a decision row that does not exist. Retrofitting a delay later into a page whose headline is "within seconds" costs more than defining it now. With a 2 to 4 minute lag that branch is the less likely one, which is why this is minor.
  - **Recommendation:** Apply the delay in the public read path on the server (one configured public delay, 0 until the gate) so the page and the API stay in step and the frontend does not change at the gate. Delete the dangling risk row or add the decision row.
