### Blockers

- **W1 [critical] data-integrity: no live call is graded in public until the backtest shows an edge** (AR, FP, CB, AM, PH). Per-signal results and Track record come from engine PR 10's outcome revisions; D3 "shares the engine's evidence gate"; with no edge it "waits for the rethink". So from the soft launch (growth: "the public record starts that day") until PR 10, and for good if there is no edge, calls go ungraded. Grading needs bars and arithmetic, not an edge, and growth's gate check 2 (8+ weeks live) needs it.
  - Fix: ask the engine to move live grading (move vs benchmark at each window after costs, hit or miss, written as revisions) into PRs 6-8 with no gate. Split D3: Track record and per-signal results ship with grading, at or just after the cutover; Evidence, the report, tiers and typical moves wait for PR 10. Start Track record small (one line for all sent alerts, the alert list, misses kept); add per-tier lines once each tier has about 30 live alerts. Alerts made before tiers exist stay "untiered" and are never tiered afterwards, which would be look-ahead (earlier reviewer, #18).
- **W2 [critical] security: D1 publishes raw prices against the agreed rule** (all six). `/api/v1/bars/<symbol>`, the "1-minute prices since the post" chart, `/api/v1/prices/latest` polled every 5 s (hookups note, 00:05), "entry price" in the Evidence drill-down, and the entry price inside public alert.v1 outcome revisions. A % series plus any one free quote rebuilds the prices, so even a minute-level % chart may count as Alpaca's data (unverified). Also, "minute bars cover every post since 2022" is false for the site: the database keeps 1-minute bars only for alert windows and 30 days. The earlier reviewer found Alpaca's support page "redistribute-alpaca-api" quoted in search results as "You cannot redistribute Alpaca API data, either for business purposes or in general" (the page itself is blocked from the sandbox, so a person should read it).
  - Fix: no public endpoint returns a price, a bar or an entry price. Cut `/bars` and `/prices/latest`. The signal endpoint returns computed moves (vs benchmark at each window, plus the latest `alert_progress`, refreshed every 60 s). Until Alpaca answers in writing about derived series, the chart is the window points (a small inline SVG), not a minute series. Add a test that walks every public response schema and fails on a price-like field. Entry price stays internal (same fix as E14).
- **W3 [critical] data-integrity: the signal page's headline answers a question the engine can't** (FP; AR as major). "How much of the typical move is left" and "is it still worth trading?" subtract the move so far from the typical move, which is not the expected remaining move; the backtest never measures it. It reads "all of the move left" for the 69% of posts outside market hours, and per-security timing language is what growth says strains the publisher exclusion (unverified). The cumulative "what following every alert would have returned" curve is a hypothetical-performance claim.
  - Fix: the page answers "what was called, on what evidence, and how did it do". Headline = the call, the move since the post vs benchmark with its as-of time, and how similar past posts moved at each window (n and tier). Drop "left", "still worth trading" and that decision row. Replace the cumulative curve with hit rate and median move per window; put the curve on the lawyer's list for the gate.

### Risks

- **W4 [major] scope: D1 is an unsized mega-PR on the cutover path** (all six). Before growth: a new React app, the live list with filters, new bar, tab counter, market clock, split view, a seven-section signal page, two endpoint families, previews, deletion of the old site, Vitest, Playwright, CI. Growth adds ten more items that "should fit inside a PR the plan already has". No PR has a size. Precedent: #111 (44 files, +4,160 lines, merged 7 seconds after opening) was followed by a path-traversal fix, a chart rebuild, hand-run migrations, a still-open Hooks bug (#214) and three polish PRs in four weeks.
  - Fix: D1 = the cutover minimum, sized: the signal page every Telegram post links to, a plain alert list, `/api/v1/signals`, the domain with canonical tags, server-injected text previews for `/s/`, the footer disclaimer and one /about page, visit counts. Everything else goes in a "launch" PR timed with engine PR 10 (report, ticker pages, sitemap, typical moves, README). Size every PR.
- **W5 [major] architecture: the cutover couples the engine to D1 and the site has no rollback** (AR, FP, PH, PC). The web service first meets the engine database on cutover night; N2 needs the same variable earlier; D1 deletes the old site, so the engine's rollback ("old workers back on") leaves a new site reading a database that stopped updating. The optional real-data check spins up a temporary Railway service with no removal step.
  - Fix: Chris sets `WEB_DATABASE_URL` at engine PR 7, when he creates the engine database; the web app builds its DB engine lazily and boots without it. N2 and D1 run on the real web service against shadow-week data (no temporary service). Keep the old frontend files until PR 11, which already deletes old code; D1 only repoints the static folder and build command, so a site rollback is a config change. Write a numbered cutover sequence; the web service holds both database variables until PR 11 (the old Telegram route imports `notifications`).
- **W6 [major] performance: launch traffic will rate-limit every visitor at once** (all but AM). Checked: `api/rate_limit.py:10` keys on slowapi `get_ipaddr`, which looks for an `X_FORWARDED_FOR` header (underscores) that proxies never send, then falls back to the connecting address; uvicorn runs without proxy-header trust, so that address is Railway's proxy. Every visitor shares one bucket, and any client can pick its own bucket by sending that header. Each tab polls every 5 s into one replica; the load estimate is "inference, not measured". The old client retries 4xx twice (#228 L6).
  - Fix: in the first PR that creates `/api/v1` (one owner, shared with N2), key the limiter on the trusted proxy hop, with a two-address test. Cache the changes response for 2-5 s in-process and send `Cache-Control: public, max-age`; return `head_seq` with list responses; poll the home list every 15-30 s, pause when hidden, back off on 429 and never retry it. Load-test a few hundred simulated tabs before the public launch.
- **W7 [major] scope: cut the Status page (D2)** (all six). It is the fourth surface for facts Chris reads in the engine CLI, health endpoint and operator messages, and it names each mirror and "how often each was first", publicly advertising that the product runs on CNN's and trumpstruth's feeds (CNN's live-feed terms reportedly bar commercial use, unverified). Meanwhile nothing watches the public site.
  - Fix: delete D2, `/api/v1/status/engine`, N2's `/status/outlets` and N4's `engine_status` (or point it at the engine's health query). Keep the header freshness dot from one field on an existing response and one line on the Record page, "median post-to-alert time this week", naming no feed. The engine checks the site's health endpoint every minute and messages Chris after three failures (pairs with E10).
- **W8 [major] scope: about ten page types, mostly views of one table** (all six). Live, Signal, Evidence, Track record, Status, Connect, plus growth's ticker, topic, report and methodology pages. Evidence, the report, ticker and topic pages all read `backtest_summary`; Connect is a page of links on its own PR (D4) gated on N3 and N4. Each page also needs a public `/api/v1` contract. Precedent: the 2026-02-22 review named "fragmented across 4 pages" as Chris's pain; 37 UI PRs and five looks in five weeks followed.
  - Fix: six page types in three PRs: home, signal, ticker (`/t/<slug>`, also the Evidence drill-down), Record, Report (Evidence table plus the written report) and About (methodology, disclaimer, positions notice, follow and agent links). Cut D4, topic pages (a filter), the evidence-layer switch (show the layer alerts quote plus the live record; others in the downloadable report), dark mode for now. Show cells with 20+ cases by default and colour only those that pass BH. Dashboard endpoints drop from eight to four (signals, one signal, evidence with filters, track record).
- **W9 [major] scope: the site is built as a live terminal when its job is the record and turning visitors into followers** (AR, AM, FP). "Show it within seconds", a split view, a "new" bar, a tab counter, infinite scroll, for 2-5 sent alerts a day that already arrive by Telegram push. Cold visitors from X, Reddit and HN get no pitch, no record and no follow button; follow links arrive last, in D4.
  - Fix: home = the one-line promise, the record headline, the latest calls (updating quietly), Telegram and X follow buttons in every page's shell from D1. Drop the split view, "new" bar and tab counter; an "older" button replaces infinite scroll.
- **W10 [major] scope: "All posts" turns the site into an indexed mirror of Trump's feed** (AR, AM, FP). The filter is the only reader of `signals.seq`; with growth's sitemap it makes 36,580 full-text pages, against growth's "quote a line and link"; pre-cutover pages show a backtest-layer call with no label.
  - Fix: drop "All posts" (and `signals.seq`, see E4). Public pages only for signals with a call; quote at most about 280 characters plus a link; no-call and pre-cutover pages noindex and out of the sitemap, labelled with the layer that made the call and "never alerted".
- **W11 [major] architecture: link previews have no mechanism, and the stack predates growth** (all six). The SPA's catch-all returns the same `index.html` for every path (api/main.py:80-95); crawlers don't run JavaScript, so every shared link shows one generic card. Growth wants server-rendered titles and images for five page types. Generated images earn little now: our own X posts carry no links ($0.20 a link), platforms cache previews, and a cached move goes stale.
  - Fix: decide before D1, as a recorded decision. Either keep the SPA and inject per-URL title, description, canonical and og tags in the catch-all from the same queries, or render pages on the server (FP's from-scratch pick: FastAPI templates plus a little JS, previews and SEO for free, no Node toolchain). Either way: one static card image per page type, generated images only after visit counts show sharing; a JSON 404 for `/api/*` before the catch-all; a test that fetches `/s/<id>` without JavaScript and asserts the tags.
- **W12 [major] compatibility: links in channel posts are permanent, but the URL scheme isn't settled** (all six). `/s/<signal_id>` carries `truth_social:<id>` with a colon; the engine adds `alerts.public_id` "for share links". N1 posts links from the shadow week; the domain is only being registered now.
  - Fix: before N1 is written, one canonical URL that works for every page-worthy signal, with no colon; `public_id` only as a 301 short link, or cut. The domain is live before the first channel post; no post ever links to `*.up.railway.app`. One URL-builder shared by N1, N5 and D1 tests.
- **W13 [major] data-integrity: the Telegram "receipt" isn't one** (AR, FP, AM, CB). Channel posts are edited in place as results arrive, and Telegram doesn't show the original.
  - Fix: the signal page shows revision 1 verbatim with its time as the receipt; label the Telegram link "sent here"; post results as replies, not edits (notification change; pairs with E20).
- **W14 [major] stocks-only windows and SPY are hard-coded** (all six). The approved "Result windows" row, the market clock and "one column per window" can't hold crypto's 5m-7d set against BTC, around the clock.
  - Fix: windows, benchmark and calendar come from the API per instrument; split Evidence and Record by asset class; the verdict reads `alert.market_open`; define the cumulative line. Build no crypto columns until Chris decides; then it is data, not UI work.
- **W15 [major] architecture: nobody owns `/api/v1`** (AR, PH, PC). Where its code lives, how it imports the engine's models, what tests it (the web service has no CI), who owns paging, errors, `head_seq`, `stream_id`, limiter, caching and CORS. D1 and N2 write routers in parallel. `api/dependencies.py:7` imports `shit.db.sync_session`, which opens a pool to the old database at import. The doc says "read-only role" while the agreed role writes the `app` schema. CORS defaults to the old Railway URL; HSTS `includeSubDomains` will bind every subdomain of the new domain.
  - Fix: `/api/v1` lives in the engine package (for example `engine/api`, imported by the web service) and runs in engine CI against the engine's migrations under the real roles, with a privilege test. One owner for conventions, set in whichever of D1 and N2 lands first; the agent guide's endpoint list comes from OpenAPI. Open CORS for GET on `/api/v1`; drop `includeSubDomains` until known safe; validate symbol and topic against the instrument table. From the earlier reviewer (#5, #6): `GRANT SELECT ON ALL TABLES` misses tables added by later migrations, so the role setup needs `ALTER DEFAULT PRIVILEGES` (or each migration grants); and the web role must not be able to read other people's webhook URLs or secrets (revoke SELECT on those columns or serve views).
- **W16 [major] error-handling: no empty, pending or small-sample states** (PC). Every earlier dashboard died on empties (UI_SYSTEM_ANALYSIS: 9 of ~1,548 outcomes; #68, #76, #104, #106). Day one is empty by construction: no live alerts, multi-day windows not matured, most cells under 20, most posts outside market hours.
  - Fix: a states table per section (no rows; window not matured, "matures Tue close"; n under 20, show the count and hide the rate; market closed; feed late), each with a component test against a seeded empty database.
