Lens key: AR adversarial-review · FP first-principles · CB cost-benefit · AM align-to-mission · PH plan-health-audit · PC precedent-check

Finding ids use M (messaging) so they don't collide with the plan's own PR names N1-N6. The lenses agree the core holds: one running number, a bookmark per outlet, a deliveries record, at-most-once to people, a dry-run switch, `notify_operator`. The problems are at the edges and in stale text.

### Blockers

- **M1 [critical] data-integrity: the public alert object would carry the raw entry price, permanently** (AR, FP, CB, PH). The doc and engine F say the first result "carries the entry price and time used"; the alert is served whole to the API, MCP, webhooks and Telegram; `alert_revisions` is insert-only behind a trigger, so a leaked price can never be withdrawn. PH adds: the filter's "tradeable now" matches neither engine field (`tradeable`, `market_open`); post links can't live in an insert-only revision; nobody owns the `AlertV1` model the schema comes from.
  - Fix before engine PR 6 freezes the shape: engine PR 6 owns `AlertV1`; it carries derived numbers only (% since post, vs benchmark, hit or miss, entry time); the entry price stays in internal tables; N2 serves the schema generated from the model with a contract test that fails on any price-like field; post links are a read-time join on `/alerts/{id}` and `/alerts`. Same fix as E14 and W2.
- **M2 [critical] architecture: the doc's cursor is the old one** (PH; AR notes it). It describes `alerts.seq`, one row per alert, and never mentions `stream_id`; the agreed design is `alert_revisions.seq`, several revisions per alert, `stream_id` on every reply. A builder following the doc would key bookmarks and `/changes` wrong, and a delayed reader couldn't publish the first call.
  - Fix: rewrite the delivery, hookup, N1-N3 and "Pull" sections on `alert_revisions`; every response carries `stream_id`; a stream change jumps push outlets to the head rather than replaying; tests for both. Stale text, not a design flaw, but it must land before N1 and N2 are written.
- **M3 [critical] data-integrity: Telegram posts are edited in place, which breaks the receipt and hides the misses** (AR, FP, CB, AM, PC; earlier reviewer #6). Edits notify nobody, so followers never see results; Telegram shows no edit history, so a rewritable post proves nothing; skipped or dropped posts leave unexplained gaps that look like deleted misses. Crypto adds updates at 1h and 4h, against the approved "no 1-hour follow-up". Precedent: PR #137 existed to give each alert notified follow-ups. Cutover hazard: switching one destination from Chris's chat to the channel makes later edits target message ids from the wrong chat (PH; earlier reviewer's blocker #2).
  - Fix: never edit a sent call. Results go out as one notified reply per alert (1 trading day for stocks, 24h for crypto), plus one daily results message that names any skipped calls and why; the Monday scorecard uses the same renderer. Result code ships with engine PR 10, runs in Chris's chat first. Store `(chat_id, message_id)` on every delivery; the channel is a new destination whose bookmark starts at the current head.
- **M4 [critical] scope: the public channel and permanent record start at PR 8, but alerts carry no evidence until PR 10** (AM; PH on undefined tiers). Every evidence-less call becomes permanent public history, the first thing a follower or reporter reads. "Sent" before tiers exist is undefined (MEDIUM and HIGH are defined nowhere; sent/FYI/suppressed have a field and no rule), and the channel path first runs in public.
  - Fix, Chris's call: either keep the channel invite-only at PR 8 (old subscribers and early followers in by link) and go public with the evidence at PR 10, or record a conscious choice that the public record includes the evidence-pending period. Either way: write the pre-PR-10 disposition rule into N1 (for example, only `sent`, labelled "evidence pending"), define MEDIUM and HIGH with thresholds in engine PR 6/10, and add a private test channel in the shadow week so the channel path is proven a week early. Pairs with E15 and W1.

### Risks

- **M5 [major] scope: defer N3 (webhooks and keys) to the paid gate** (all six; CB critical; earlier reviewer #1, #14). Keys, a registration API, signing, 24-hour retries, pausing, replay, an SSRF guard and encrypted secrets, for "only you and your own agents at first", who can poll `/changes`. It is the only reason the web role needs write access, the engine's largest new attack surface (POSTing to strangers' URLs from the alert process), and growth lists webhooks as something the paid tier might sell. Precedent: the Feb 2026 spec built email and SMS senders that nothing ever called (`notifications/dispatcher.py`, #223).
  - Fix: no N3 now. Document polling in agents.md; if Chris wants push to his own agent, one outlet configured in Railway variables (URL plus HMAC secret) on the same bookmark and deliveries row; an RSS feed of sent alerts covers Zapier, IFTTT, n8n and Discord. Drop `api_keys`; the web role stays read-only; D4 stops waiting on N3.
- **M6 [major] scope: N1 and N2 carry later work onto the critical path** (CB, AM, PH, PC). No PR is sized. N1 builds a five-field filter (tiers and `tradeable` don't exist until PR 10), edit-in-place (nothing to edit until PR 10), per-destination delay and owner columns (no `users` table until the gate). N2 bundles the schema, agents.md and `/status/outlets`, whose readers come later.
  - Fix: N1 = one Telegram outlet following `alert_revisions.seq`, a bookmark row per outlet (outlets defined in code), `deliveries`, the give-up rule, the off/dry-run/live switch, a `disposition = sent` predicate, `notify_operator`, and the one-time subscriber send. N2 = `/alerts/changes`, `/alerts`, `/alerts/{id}`. Schema and agents.md ship with the first agent consumer; `/status/outlets` goes with D2 (cut, W7). Size every PR.
- **M7 [major] error-handling: the delivery rules drop the alert that matters and contradict themselves** (AR, AM, PH, PC; earlier reviewer #4, #5). "Never retry a `sending` row" lumps definite rejections (429 with `retry_after`, connection refused, 400) with ambiguous ones (timeout after send), so one burst or one bad character loses a public call. Read literally, "skip any alert over 30 minutes old along with its updates" skips every result; anchored to alert creation, with 9 and 17-minute mirror lags, a post can reach Telegram about 47 minutes late. No rule covers an update to an alert this destination never sent. The old code abandoned relative to each horizon (`followups.py:172-187`).
  - Fix: decide once per destination when it first sees an alert (`sent`, `skipped_filter`, `skipped_stale`, `dry_run`), with age measured from `posted_at` and a limit near the engine's p95 (about 10 minutes); later revisions go out only for live-sent alerts; filters are never re-evaluated. Retry definite failures within the limit; ambiguous ones become `unknown`, counted and reported. Every skip notifies Chris and shows in the record.
- **M8 [major] error-handling: Telegram sending is greenfield exactly where the old sender broke** (PC; earlier reviewer #5). PR #52's first production deploy failed on MarkdownV2 parsing; two escapers drifted (M18); the old sender returns no message id and has no 429 handling. Messages cap at 4,096 characters; channels allow about 20 messages a minute, edits included (search results); identical edits return "not modified". The sandbox can't reach Telegram, so recorded-shape tests can't see any of this.
  - Fix: HTML parse mode or plain text with one escaper, tested on hostile samples; cap near 3,500 characters; per-chat pacing with creates ahead of edits; "not modified" counts as success; numeric chat id; a scripted live check (real post, hostile characters) in the shadow-week runbook.
- **M9 [major] architecture: two engine processes run during every Railway redeploy** (earlier reviewer #3; AR on Alembic). Railway's docs (via the earlier reviewer) say the old deploy overlaps the new one and then gets SIGKILL with 0 seconds' grace. Both read the same bookmark and both run the scheduler, so double sends and double jobs are possible, and an in-flight send leaves a `sending` row. Correction to E8: session advisory locks don't work through Neon's pooled (transaction-mode) endpoint.
  - Fix: `UNIQUE (destination, alert, revision)` with the INSERT as the claim; bookmarks advance with `GREATEST`; a lease row per outlet (and for the scheduler) instead of a session advisory lock; stop claiming on SIGTERM and set a draining period. Pairs with E9.
- **M10 [major] observability: the engine watches itself** (AR, FP, PC; earlier reviewer #12). `notify_operator` runs in the same process and uses the same bot, so a wedged loop, crash loop or Telegram outage produces silence. The failures on record here were silent drops, not duplicates (#198 neutral alerts, b1bf662 winter briefing, #215, #243).
  - Fix: a free outside heartbeat that emails Chris (pairs with E10); async clients with hard timeouts only; supervised worker tasks; notices for any skip, any `sending`/`unknown` row older than 5 minutes, and a scheduled run that didn't happen; schedules on the New York market calendar.
- **M11 [major] scope: growth's additions don't fit the alert cursor** (all six). The daily results, Monday scorecard and report thread aren't alert revisions, so they have no delivery record, switch, idempotency key or PR; the scorecard reverses the approved "weekly scorecard not kept"; putting post links into the alert would create a revision that makes every outlet act again. Per-link join counts need inbound `chat_member` updates the plan deletes (verify).
  - Fix: one results PR after engine PR 10 and the record page: a daily results message and the Monday scorecard from one renderer calling the same record query as the site, delivered through a `broadcast()` entry with a delivery row keyed on outlet and run. Start scorecards once about 20 alerts are graded. Chris confirms bringing the scorecard back. Invite links made by hand in Telegram (read counts in the admin view, verify); the audience count is one member-count call a day.
- **M12 [major] scope: X automation sits on the public launch's critical path** (CB, AM, FP, AR). The report thread is a one-off; the scorecard is one post a week. The "X gate" is written twice (growth's launch already needs the edge). X prices, free allowance and auth flow are unverified.
  - Fix: Chris posts the launch thread by hand, as he does Reddit and HN; the engine sends him the scorecard text until N5 exists. Build N5 once, as a single poster (post, reply, cap, kill switch). One sentence for the X gate. Verify price, link surcharge and auth before N5 (earlier reviewer: static OAuth 1.0a tokens avoid storing rotating secrets; strip domain-like text so posts don't become $0.20 link posts).
- **M13 [major] compatibility: the "public outlets can lag" mitigation contradicts growth's legal rule** (AM; AR). Growth says everyone in a tier gets an alert at the same moment and Chris trades only after the public alert; a delayed public lane with Chris's own chat at zero delay is the pattern growth warns against.
  - Fix: no delay column or logic now; any delay is a gate-and-lawyer decision; Chris's own destinations never run ahead of the earliest public or paid one.
- **M14 [major] architecture: one public API split across two plans, merged into the old web service** (FP, PH, PC, AR). N2 adds `/api/v1` to the live old service before PR 8, with no CI and no `WEB_DATABASE_URL`; nobody owns shared conventions; a new package named `notifications/` collides with the old one deleted at PR 11; "the engine never writes" the app tables, yet its in-process workers do. Same fix as W15 and W6: one owner, a new module with CI that boots without the database (503), a different package name, a "where it runs" table with each role's grants, a head-seq cache and correct IP keying.
- **M15 [major] security: the bot token will leak into logs** (earlier reviewer #11, #18; new to the lenses). httpx logs every request URL at INFO, and Telegram URLs carry the token; anyone with log access could post forged calls to the public channel. Fix: httpx and httpcore loggers at WARNING, a redaction filter, a test that the token never appears in logs; rotate the token at the cutover and give the bot only post rights in the channel.

### Gaps

- **M16 [major] scope: the message people read is never designed** (FP, AM, AR). Mission item 4 is "what the signal says, how it has performed, how confident to be"; the doc has no example post, no pre-evidence wording, no confidence wording, no disclaimer, no owner for the formatter. Fix: N1 ships a small template set from one `render(revision, outlet)` function with golden tests (evidence pending, evidence per tier, stock and crypto, market closed, result reply, operator notice), every public one carrying "not investment advice"; Chris approves sample renders before the shadow week. Also add the disclaimer to agents.md and the MCP description.
- **M17 [minor] scope: cut N6 (Pushover)** (all six). A private Telegram chat filtered to HIGH, with its own notification sound, does the same at $0 and no new code.
- **M18 [minor] dependencies: N4 (MCP) waits on dashboard queries its gate doesn't list** (PH, CB, FP, AM). Fix: N4 at the public launch, after the record and report queries exist, as a thin adapter over the same functions; Chris does the Registry listing by hand once the domain exists. The earlier reviewer's MCP mounting traps (#8: session manager in lifespan, allowed hosts, exact `/mcp` path) go in N4's checklist.
- **M19 [minor] compatibility: the old webhook and the subscriber message** (PC, PH). The plans disagree on whether the old Telegram webhook is kept for rollback or removed at PR 8; rollback doesn't need it (old workers send with `sendMessage`). The one-time message to old subscribers has no owner; the repo puts them at about 5 (`08_WHAT_HAPPENED_FOLLOWUPS.md:830`). Fix: `getWebhookInfo` before the cutover and `deleteWebhook` at it; the subscriber message is a short runbook script run on Railway after the old workers stop, with a sent log, a dry run, paced sends, and 403s recorded and skipped (earlier reviewer #13).
- **M20 [minor] scope: no burst policy** (PC, AR; pairs with E22). Fix: measure bursts from the archive; same ticker and direction within 30 minutes becomes FYI; overnight and low-tier posts go out with `disable_notification`; a replay test with ten alerts in two minutes and a 429 in the middle.
- **M21 [minor] cost: the budget counts X for three months only** (CB, AR). X, Railway and Neon keep billing after the build. Fix: state a monthly run rate and a stop rule next to the $250.
