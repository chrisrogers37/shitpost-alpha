## Blockers

- **[critical] scope**: The public channel and the permanent public record both start at the cutover (engine PR 8), but alerts carry no evidence or tier until engine PR 10. The engine plan says so itself: "Until PR 10, alerts say that evidence is still being built." Mission item 4 is alerts "that carry that evidence", and the growth thesis is "win on evidence". The growth plan makes PR 8 a "soft launch": the channel goes public and "the public record starts that day". Revisions are insert-only and growth promises misses stay up, so every evidence-less call from PR 8 to PR 10 becomes permanent public history, the first thing any follower or reporter reads. It is also undefined what "sent" means before PR 10, because disposition and min-tier filters depend on tiers that do not exist yet. Either every ticker-naming post goes to the channel or nothing does. Separately, the shadow week sends only to Chris's private chat, so the channel path (admin edit right, channel id vs username, permalinks) first runs in public at the cutover. The plan's success criteria (fake outlets, a clean shadow week) can all pass while the first public impression fails the mission.
  - **Recommendation:** Decouple "cutover" from "public". At PR 8 point the Telegram destination at an invite-only channel and let old subscribers and early followers in through the named invite links. Flip it public, and start the public record and public launch, together at PR 10 or the first evidence-bearing alert. Write the pre-PR-10 disposition rule into N1 explicitly: for example, model calls go only to the admin and private channel, labelled "evidence pending". Have the track-record headline count only alerts that carry evidence. During the shadow week add a second destination pointing at a private test channel, so the channel path is proven a week early. This is a sequencing decision, so it costs nothing, but it has to be settled with the growth plan before either is edited. If Chris wants the public soft launch at PR 8 anyway, record it as a conscious choice that the permanent record includes the evidence-less period.

## Risks

- **[major] scope**: N3 (signed webhooks and keys) and N4 (MCP server) are the plan's largest tangential block, and they serve the least-evidenced audience. The mission lists no agent consumer. The growth plan ranks developers and agents as one of five audiences and puts webhooks and higher API limits into the paid tier only if the edge is slow, a decision made at a gate that is 8+ weeks live, 2,000 followers and a lawyer away. Yet N3 is scheduled right after the cutover. It brings an outbound-POST service that shares Railway's private network with the engine and database: key hashing and a key command, Standard Webhooks signing with a fresh signature per attempt, 24-hour retries, pausing, replay, test events, an SSRF guard (is_global, pinned connect, no redirects) and encrypted signing secrets with a key variable. That is probably the second-largest PR after N1 (inference), and its main outcome is new attack surface for zero current users. N4 adds a second public surface (/mcp with its own limit, route ordering ahead of the dashboard catch-all) plus a registry listing under a domain that does not exist yet. Cutting them saves effort and risk, not money (N3 and N4 cost $0).
  - **Recommendation:** Treat N2's public pull API, JSON Schema and agent guide as the entire agent surface for now: no key, no outbound fetch, no secrets. Move N3 behind the growth plan's paid gate (rescoped by what the gate sells) or until a real builder asks for push. D4 Connect then waits on N2 only. Defer N4 until after the public launch, and build it only if the Show HN or registry listing needs it, as three read tools over queries that already exist (latest_alerts, get_alert, track_record). That removes the SSRF and secret-storage design from the stress-test surface entirely.

- **[major] scope**: The growth plan's change to N5 does not fit the plan's architecture or its "fits inside an existing PR" rule. N5 is specified as MEDIUM and HIGH alerts as plain posts plus a 1-day reply, following alert revisions. Growth moves X to the public launch for the report thread, daily results and a Monday scorecard, with per-alert posts still waiting. The report and the scorecard are not alert revisions. They are scheduled, aggregate publications that read the track-record query (engine PR 10, D3). The notification plan explicitly deleted the weekly scorecard ("nothing is ported"), and growth now asks for it back, plus a Telegram copy. Automating X before the account has a follower is the overbuild: a pay-per-use API client, a post cap, a kill switch and a dry-run week, to publish roughly one post a day. A scorecard sent in the first weeks will also rest on a handful of graded alerts, which is noise when misses are being kept on purpose.
  - **Recommendation:** For the first 6 to 8 weeks the engine's scheduler produces the Monday scorecard and the daily-results text as plain text, N1 sends it to the Telegram channel, and Chris pastes it into X, as he already posts Reddit and Hacker News by hand. Build the X API outlet only once manual posting is a real chore and followers exist, and recheck pricing then. If it is built, specify it as a "broadcast" outlet with its own delivery key (kind, period) and not as an alert-revision follower, and say in the plan which PR owns the scorecard job. Do not start scorecards until there are enough graded alerts to show a count and an interval, for example 20.

- **[major] compatibility**: The notification plan's mitigation for "Giving the edge away" contradicts the growth plan's legal rules. The notification plan says that if the backtest finds an edge worth protecting, "public outlets can lag by a set delay". Growth says every alert goes to everyone in a tier at the same moment, "You can trade on them only after the public alert is out", and cites the December 2022 SEC and DOJ influencer case. A delayed public lane with Chris's own destinations (admin chat, phone) at zero delay is exactly the pattern growth warns against. The note also adds a per-destination delay column to `destinations`, which growth says is used "only after the gate".
  - **Recommendation:** Delete the "public outlets can lag" mitigation from this plan and do not build a delay column or delay logic in N1 to N3. Any lag becomes a growth-and-lawyer gate decision, and the operator's own destinations must carry the same timing as the public channel. State that in N1's spec so the stress test checks it.

- **[major] error-handling**: The delivery rules lose the one alert that matters and let a stale alert through. "At most once to people" marks a send as sending and never retries it, which treats every failure as an ambiguous crash. A Telegram HTTP 429 with retry_after is a definite non-delivery, and Trump posts arrive in bursts of many posts per minute, so 429s on one channel are the likely failure, not a crash. The bot account also sends operator notices from the same token. A silent drop of a HIGH alert is the worst failure for a "signal I'd trade on", and the operator-notice list does not include an orphaned sending row or a skipped alert. The 30-minute give-up is also ambiguous about its start. If it counts from alert creation, and the mirrors were 9.4 and 17 minutes late on two of three measured posts, a Telegram alert can arrive about 47 minutes after the post. That is far outside "within minutes" and the engine's own 10-minute p95 target.
  - **Recommendation:** Split failures into definite (429 and connection refused before any request body is sent: retry within the give-up age, honouring retry_after) and ambiguous (timeout after send: leave as sending). Add an operator notice for every orphaned sending row and every skipped alert, and show skipped alerts in the record so "every call is public" stays true. Anchor the give-up age to posted_at, not alert creation, and set it to the engine's p95 target (about 10 minutes) until the backtest shows how long the edge lasts.

- **[major] performance**: Launch day is the plan's untested load case, and the rate limiter it would reuse is broken in the way that matters. The dashboard polls /api/v1/alerts/changes every 5 seconds per visible tab with no login, and the plan's answer to load is "one indexed query, under per-IP limits". The mission's growth goal means a Show HN or Reddit crowd lands on the live list: hundreds of distinct IPs, each polling every 5 seconds, straight to Neon. Per-IP limits do not help against a crowd. The only limiter in the repo is also unreliable: `api/rate_limit.py:10` uses slowapi `get_ipaddr`, which looks for the header "X_FORWARDED_FOR" with underscores (checked in the installed slowapi). A real request carries "X-Forwarded-For", so that lookup never matches and the key falls back to `request.client.host`, which behind Railway's proxy is probably one shared address. If so, a limit like the old feed's 60 a minute with a 12-a-minute poller per tab would return 429 to everyone once about 5 tabs are open. The notes already flag the real-client-IP need, but the doc's risk row still relies on it.
  - **Recommendation:** N2's verification should include a load test: 500 simulated pollers at 5 seconds with distinct IPs against the sandbox database. Serve /alerts/changes from a short in-process cache keyed by `after`, plus a cheap "head seq" check that most polls hit. Key rate limits on a header verified on Railway. Make the dashboard back off on 429 and when idle.

- **[minor] scope**: N6 (Pushover phone push) does not earn a PR. It is $5 plus a vendor, a key, a PR and a test surface to make HIGH alerts "stand out" on one phone. The plan already makes a destination a row with a tier filter. A second Telegram destination (Chris's private chat with the bot, HIGH only, with its own notification sound or a Focus exception) delivers the same thing with no new outlet code.
  - **Recommendation:** Cut N6. Revisit it only if a missed HIGH alert actually shows up in the delivery record.

- **[minor] scope**: N1 and N2 are slightly over-general for what the cutover needs. N1 builds ticker, direction and tradeable filters for a single destination. Direction is ill-defined when an alert names several instruments, and the old bot's direction filter never matched, which is a bug the plan says it avoids. N2 ships the JSON Schema, the agent guide and /api/v1/status/outlets, but D1 only needs changes, list and detail. The schema and guide belong with the first agent consumer, and status/outlets belongs with D2.
  - **Recommendation:** N1: destinations (kind, state, bookmark, mode) and deliveries (needed for edit-in-place) with one filter, disposition plus min tier. Add the other filters when a second destination needs them. N2: ship changes, list and detail now, and move the schema, agent guide and status/outlets to the PRs that consume them.

## Gaps

- **[major] scope**: The plan specifies the pipes in detail and never specifies the message. Mission item 4 names the content: "what the signal says, how it has performed historically, and how confident to be". The doc has no example Telegram post, no statement of how confidence is shown (the dashboard plan says the model's confidence is never a headline, and tier plus the move left is), no pre-evidence form, and no rendering of results. It does not say who owns the formatter (engine PR 10 mentions formatter tests, N1 mentions the post), though Telegram, X and the dashboard's preview cards must say the same thing. It omits the disclaimer line growth wants on every outlet, Telegram's 4096-character limit and escaping, and the link to /s/<public_id>. Edit-in-place also hides results: Telegram edits send no notification, so a win or a miss that arrives a day later is invisible to anyone who does not scroll back, while growth's loop depends on results being seen. This is the part of the plan that attracts followers, and it currently has none of the plan's attention.
  - **Recommendation:** Add a message spec to N1 with three worked examples (an evidence-pending alert, an evidence alert, a result update). Put one pure render(revision, outlet) function behind golden-file tests, shared by Telegram, X and the dashboard's preview cards. Decide how results surface: for example a short threaded reply that notifies (and the edit), or a daily results message, with the disclaimer on every public post.
