## Risks

- **[major] scope**: The plan repeats a shape this repo has already paid for: build a multi-outlet framework first, then use one outlet. The Feb 2026 alerting spec (`documentation/planning/06_ALERTING_SYSTEM.md`, 3,352 lines, header "MOSTLY COMPLETE" as of 2026-02-13) covered Telegram, email, SMS and browser alerts. Only Telegram ever ran. `notifications/dispatcher.py` (437 lines, email and SMS) has no caller outside tests (grep on main 139b145; tech-debt M20, #223 open). Browser alerts went with the Dash UI (a537bc4). The April brainstorm's FCM push (`10_PUSH_NOTIFICATION_GATEWAY.md`, 1,334 lines) and batching (`09_SMART_ALERT_BATCHING.md`, 1,012 lines) were never built. The source side shows the same pattern: `HarvesterRegistry` plus `twitter_harvester.py` (306 lines) is never invoked (M24, #224). The current plan has 6 PRs, 3 new tables, 4 push outlets and per-destination filter, bookmark and delay machinery. The audience it serves today is about 5 subscribers (`08_WHAT_HAPPENED_FOLLOWUPS.md:830`) plus one channel at launch. N3 (keys, encrypted secrets, URL guard, 24-hour retries, pausing, replay, test events) has no named consumer, and "your own agents" can already follow N2's changes endpoint.
  - **Recommendation:** N1 ships one Telegram destination (your chat for the shadow week, then the channel) with its bookmark, the deliveries record, the off/dry-run/live switch and give-up age, with that destination's config kept in one row or one setting. Build the general `destinations` table, per-destination filter and per-destination delay only when a second destination exists (N3 or N5). Keep N2, because the dashboard needs it. Defer N3 until a named person or agent asks for push; N4 until someone wants to connect (the growth plan's MCP Registry listing is the only pull). Cut N6 until you miss an alert in practice, since you can be in the channel from your phone.

- **[major] error-handling**: Telegram sending is greenfield in exactly the places the old sender broke, and the plan's test method cannot see those failures. The first production deploy of the old bot failed on parse mode (PR #52 changed Markdown to MarkdownV2 and added escaping in the deploy PR itself). Two escapers then drifted (M18: `_escape_md` vs `escape_markdown`), and `/start` injected unescaped names (L2). The old sender (`notifications/telegram_sender.py:26-81`) returns only `(ok, error)`. It has no message id (`08_WHAT_HAPPENED_FOLLOWUPS.md:822` deferred storing it to "v2"), no 429 or `retry_after` handling, and a 10 s timeout whose outcome is ambiguous because the request may have posted. The plan needs all three for edit-in-place, bursts and arbitrary post text. Telegram is unreachable from the sandbox, so "requests checked against recorded API shapes" cannot catch a parse rejection. Separately, the rule "a delivery left in sending is never retried" puts definite rejections (400, 403, 429, where nothing was posted) in the same bucket as ambiguous outcomes (timeout, 5xx, crash). One bad character or one flood-wait therefore silently drops an alert.
  - **Recommendation:** In N1, split the outcomes. A definite rejection is retried: 429 after `retry_after`, 400 parse error resent once as plain text, 403 pauses the destination and notifies you. An ambiguous outcome becomes an `unknown` status that is counted and surfaced. Use HTML parse mode or plain text with one escaper, tested on hostile samples (underscores, dots, parentheses, `<`, `&`, `$TSLA`, emoji, the 4,096-character limit). Store (chat_id, message_id) on each delivery. Because the sandbox cannot do it, put a scripted live check in the shadow-week runbook: a real post, a real edit, and a post containing the hostile characters, sent to your chat.

- **[major] observability**: The failure class on record is silent non-delivery, not duplicates, and the plan hardens against duplicates. Duplicates exist only as a theoretical risk (#202 and #171 are open; I found no incident report in the issues I searched). What did happen:
  - Alerts went out neutral with an empty thesis on the live event path (#198, `notifications/event_consumer.py:63`), with no error raised.
  - The morning briefing silently never sent on any winter weekday, because its time guard rejected the 7:30 ET firing and nothing "failed" (b1bf662, #230 L3).
  - Votes never matured (#215).
  - The webhook secret was "verified" (bb0d76c, #162) but never registered with Telegram (L1). The fix (#241) then created a new silent-death path (#243, open).

  The plan's rules (at most once, 30-minute skip, never retry `sending`) all favour dropping over repeating. Its operator notices cover infrastructure faults and run inside the engine process. A skipped or ambiguous delivery, a guard that quietly rejects a scheduled run, or a dead engine process produces no notice. Today's `railway.json` default is `ON_FAILURE` with 10 restarts, then the service stays down. The plan does not say what the engine service uses.
  - **Recommendation:** Record every skip, give-up and ambiguous outcome with a reason in `deliveries`, and call `notify_operator` for four cases: any alert skipped for age; any delivery stuck in `sending` or `unknown` for more than 5 minutes; no revisions from the expected daily results run (a no-show check, because a guard rejection is not a job failure); and a heartbeat check outside the engine process on `/api/v1/status/outlets` (a dead engine cannot announce itself). Run the daily results and the Monday scorecard on an America/New_York schedule tied to the market calendar, not a fixed UTC time, and test winter, summer and half-days. Decide "empty week" from numbers. The old scorecard matched the string "Total Predictions: 0" (`scorecard_service.py:115`), and `_extract_scalar` turned a real 0 into NULL (`notifications/db.py:39`).

- **[major] performance**: The mitigation for "agents polling hard" rests on a limiter that an earlier attempt got wrong. #163 (6a9620f) switched slowapi to `get_ipaddr` "for correct client IP behind reverse proxy" (`api/rate_limit.py:10`; `requirements.txt:51`, slowapi unpinned). In slowapi 0.1.10, `get_ipaddr` only looks for a header literally named `X_FORWARDED_FOR` (underscores). I ran it in the sandbox: a request carrying `X-Forwarded-For: 203.0.113.9` from peer 10.0.0.1 is keyed on 10.0.0.1. Unless Railway behaves differently (not checked here), every visitor shares the proxy's bucket. The plan has each visible dashboard tab poll `/alerts/changes` every 5 s (12 requests a minute) and agents every 5 to 15 s, with "per-IP limits" as the control. The existing feed limit is 60/minute (`api/routers/feed.py:14`), so five viewers could rate-limit each other and one hostile agent could rate-limit everyone. The planner's note records that the limiter keys on the proxy, but not the cause or the polling arithmetic.
  - **Recommendation:** In N2, stop depending on client identity for load control. Serve `/alerts/changes` from a 1 to 2 second in-process cache so cost does not scale with viewers. Give the polling endpoints their own limit sized for 12 requests a minute per viewer, and return `Retry-After`. Fix the key function (read the real client hop, test it with a header-bearing request, pin slowapi). Confirm which header Railway sets before choosing.

- **[major] data-integrity**: The update rules contradict themselves, and edit-in-place drops what the old follow-up feature was for. The plan says Telegram, X and phone "skip any alert more than 30 minutes old when its turn comes, along with its updates". Results arrive on later trading days, so read literally every result update is skipped. The old code handled this correctly: `followups.py:172-187` abandons relative to each horizon's own expected time (`EXPECTED_OFFSETS` 2 h, 48 h, 336 h, plus a 48 h deferral, lines 24-29). The plan's flat 30-minute rule has no such reference. Telegram does not notify on edits, whereas PR #137 existed to give each alert three notified touchpoints (`08_WHAT_HAPPENED_FOLLOWUPS.md`, Motivation 3). Edited-in-place results will be invisible to followers who are not looking at the channel. That weakens the growth plan's "results are posted whether the call was right or wrong" credibility device.
  - **Recommendation:** Say that give-up age applies to the `created` revision only (30 minutes from first-seen). For a result revision, measure from its own creation time, with a limit in hours. Decide how results are shown: post each daily result as a reply to the original (`reply_to_message_id`, which notifies and costs the same as an edit), optionally also editing the original once for the permanent record, or accept edit-only and state that results do not notify. Add a test: an alert from yesterday plus a new result revision must post.

## Gaps

- **[minor] compatibility**: The old webhook has a history of silent edges, and the plan and engine plan disagree about it. One inbound route produced four issues in three months: #145 (May 27), #156 (closed May 30 by #162/bb0d76c), #232 (Jul 23) and #243 (Aug 21, open). #162 verified a secret that `setWebhook` never sent (L1). #241 (e63edf0) fixed registration, but a redeploy without re-running `python -m notifications set-webhook` kills the webhook silently (#243). The notification plan keeps the route "through the clean week so a rollback still works". The engine plan says at PR 8 "The old Telegram webhook is removed" (`source-engine.md:240`) and at PR 11 deletes the route "which rollback needed until then" (`:242`). Whether the old webhook is alive today is unverified. Alerts do not need the webhook, only bot commands do.
  - **Recommendation:** Take the webhook out of the rollback story: rollback means switching the old workers back on, and they send with `sendMessage`. Before cutover, run `getWebhookInfo` (`last_error_message`, `pending_update_count`) to learn the real state. At cutover the runbook calls `deleteWebhook` on Telegram's side, and PR 11 deletes the route. Make both docs say the same thing. Any future signing or webhook secret gets a runbook line "changing this means re-registering X" and an operator notice if the first delivery after a change fails.

- **[minor] scope**: There is no burst policy. The April brainstorm called bursts the top user-experience problem ("clusters of 3-8 posts within 15-30 minute windows", `09_SMART_ALERT_BATCHING.md:11-21`), with no numbers behind the claim, and never built anything. Under this plan a burst runs through one serial worker per destination with a 30-minute give-up. The tail of a burst is therefore the most likely thing to be skipped, and on a public channel fatigue shows up as unfollows. The growth plan expects 2 to 5 MEDIUM or HIGH alerts a day, which may make this moot.
  - **Recommendation:** Do not rebuild the old batch buffer with LLM summaries. Measure burst frequency from the CNN archive the engine is already importing. If bursts are real, add one line to the engine's disposition rule (same ticker and direction within 30 minutes becomes FYI). Add "10 alerts in 2 minutes, with a 429 in the middle" to N1's replay test so the skip behaviour is seen before launch.

The link goes to every `is_active` chat as plain text, sent one at a time with about 100 ms between sends (the old follow-ups used `sleep(0.1)`, `followups.py:532`), each result logged. At 10 chats or fewer this is a roughly 30-line one-off script in the runbook, not a feature.

- **[minor] compatibility**: Do N2 and N4 live in the old `api/` package, and what tests them before the cutover? N2 adds `/api/v1` routers and N4 mounts `/mcp` "ahead of the dashboard's catch-all" in `api/main.py`, which is the live old web service. N2 merges before PR 8. The engine plan relies on "No engine PR edits `api/` or `frontend/`, except PR 11" (`source-engine.md:267`) and on engine PRs being invisible to the old services. The old code has no CI (#244), and every merge to main redeploys all 12 services. `api/main.py` is the file #241 last changed, and the same service hosts the webhook route that rollback leans on. Before PR 8 the web service also has no `WEB_DATABASE_URL` (set at cutover, `source-engine.md:240`), so N2 cannot read the engine tables yet. Suggested answer: put `/api/v1` in a new module the old services never import, joined by a one-line include, and get CI on it first.
