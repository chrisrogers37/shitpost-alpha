## Risks

- **[major] architecture**: The growth changes add things the "one running number" design has no place for. The plan's whole delivery model follows `alert_revisions.seq` (Notifications §How an alert goes out; notes/notification-plan.md "outlets ... follow alert_revisions.seq"). The growth row for Notifications adds three things that are not alert revisions. (a) **Non-alert posts**: the report thread, "each day's results" on X, and a Monday scorecard to the channel and X. The scorecard reverses §What we don't keep, which drops "the weekly scorecard", and §What you approved ("It replaces ... the weekly scorecard"). These posts have no object, cursor, idempotency key or give-up rule. A scheduler catch-up after a restart ("a run missed during a restart is caught up once", Engine §A) can post Monday's scorecard on Tuesday or post it twice. (b) **"Each alert's public post links in the alerts API"**: only the delivery worker knows the Telegram or X message id, and it is not the engine. If the link goes into `alert.v1`, it needs a new revision. That bumps seq, every outlet's bookmark sees a "change", and the Telegram worker re-edits its own post: a feedback loop. If the link is joined from `app.deliveries` at read time, `/alerts/changes` followers (the dashboard included) never learn it. (c) The **per-destination delay** column for a paid tier that may never exist. The growth plan says "each item should fit inside a PR the plan already has". For notifications that is not true for the scorecard job or for the audience count (next findings).
  - **Recommendation:** Before N1 is written, decide in the plan: (a) Scheduled posts (scorecard, launch report) go through the outlet's send function directly. Each gets a `deliveries` row keyed on (destination, job_run_id) with a unique constraint, so it is at-most-once and never a fake alert revision. Keep only the Monday scorecard and drop "daily results" on X until per-alert X posts exist, because results of calls nobody on X saw are noise. The scorecard ships with the engine PR 10 / public-launch PR, not in N1. (b) Post links are derived at read time from `app.deliveries` (Telegram's public URL is `t.me/<channel>/<message_id>`). Serve them on `/alerts/{id}` and `/alerts` only, never as an alert revision, and document that `/changes` does not carry them. (c) No delay or owner columns in N1's `destinations`; add them in the paid-tier PR at the gate.

- **[major] data-integrity**: Editing Telegram posts in place undermines the receipts the growth plan sells. §Outlets says each Telegram alert is "edited in place as each day's results arrive". Engine §F makes the first call immutable so the record can be checked ("the call as it first went out can never be edited"). Growth says "every result is posted where the alert went", "misses stay up", and the Telegram post is "the receipt" (growth change list, Dashboard row). An edit fails all three. Telegram does not notify subscribers of edits, so followers never see the misses. Telegram also shows no public edit history, so a "receipt" we can rewrite proves nothing. Crypto (notes/notification-plan.md: outcomes at 1h/4h/24h/3d/7d) adds intraday updates. That contradicts the approved "there is no 1-hour follow-up" (§What you approved) and raises edits to five or more per alert.
  - **Recommendation:** Never edit the call message. Post exactly one reply to it with the headline result: 1 trading day for stocks, 24h for crypto, the same choice the plan already makes for X. Leave every other window to the signal page and the Monday scorecard. Drop all result code from N1, because results only exist from engine PR 10 (Engine §F "Outcome updates. From PR 10"). Ship the result reply with PR 10, and run it to the admin-chat destination for a few trading days before enabling it on the channel. Today the first live run of results code would be in the public channel. Re-confirm with Chris that crypto results replace "no 1-hour follow-up".

- **[major] scope**: Defer N3 (signed webhooks and keys) to the paid gate. Nobody is waiting for it: "Keys: only you and your own agents at first" (§What you approved), and those agents can poll `/alerts/changes` every 5 to 15 s at "one indexed query" (§For agents). Growth's money plan lists "webhooks" as something the paid tier may sell, depending on where the edge is (Growth §Money, Step 2). N3 is also the plan's largest attack surface: an SSRF guard with resolve-then-connect pinning and no redirects, at-rest encryption with a key in a Railway variable, hashed keys, 24-hour retry, pausing, replay, test events and at-least-once semantics. And it is scheduled "after the cutover" with no edge gate (§Build). If PR 10 finds no edge, it was built for nothing. Deferring it also lets the public web service hold no write grants: once webhook registration is gone, nothing on the web service writes the database, so `WEB_DATABASE_URL` can be SELECT-only on both schemas until accounts exist (Engine §H "Database access").
  - **Recommendation:** Move N3 behind the growth plan's paid gate, and build it only if the gate picks "webhooks/API limits" as the paid product. Drop `api_keys` from the engine's PR 1 app schema. Shrink `destinations` in N1 to one bookmark row per fixed outlet (admin chat, channel, later X), with each outlet's filter in code. A data-driven filter/delay/owner per destination only pays off for self-serve webhooks and paid users. Make the web role read-only.

- **[major] data-integrity**: The stored alert is also the public payload, and it is insert-only, so a leaked field can never be withdrawn. The plan serves the alert "whole" to the API, MCP and webhooks ("the same alert object three ways", §For agents), and says "The first result also carries the entry price and time used" (§Hookup to the engine, Updates; also Engine §F). The growth and engine agreement is "no raw entry price publicly ... a % series plus one price lets anyone rebuild the raw prices" (Growth §Legal and data rules). As written, the first result revision publishes Alpaca-derived entry prices through `/alerts/changes`. Because revisions are insert-only behind a trigger (Engine §F), removing them means dropping the trigger and rewriting public history.
  - **Recommendation:** Treat `alert.v1` as the public contract and keep it to derived numbers only (% since post, vs benchmark, hit/miss, entry *time*). Keep entry price in `alert_progress` or `backtest_rows`, which are internal. N2 gets a contract test that fails if the published JSON Schema or any served revision contains a price-like field. Telegram/X renderers read only `alert.v1`. Lock this before engine PR 6 freezes `alert.v1` and before N2 merges. Before the cutover (PR 8) makes the site and API public, verify in writing with Alpaca whether a per-minute "% since post" series counts as displaying its data. The engine plan itself calls this open ("Whether even that is allowed is one of the stress test's checks", Engine §Data model).

- **[major] performance**: Polling every 5 s is precision that buys nothing, and at launch it is a load hazard. The dashboard polls `/alerts/changes` every 5 s per visible tab (§Dashboard touchpoints). Upstream, the mirrors are 1.6 to 17 minutes behind (Engine §Latency), so 5 s versus 30 s is invisible to a trader. The public launch is built to bring a crowd (Show HN, Reddit, reporters: Growth §Launch). At 2,000 open tabs that is about 400 requests/s, each "one indexed query" on Neon through one Railway web service. Per-IP limits (§Risks, "Agents polling hard") do nothing against many distinct visitors. The site would fall over on launch day, and Neon compute cost is unknown ("depends on your Neon plan", Engine §Budget).
  - **Recommendation:** In N2, answer "nothing new" from an in-process memo of max(seq) and stream_id refreshed about once a second, so N pollers cost about 1 query/s. Send `Cache-Control: public, max-age=5` on `/changes` so browsers or a CDN absorb repeats. Set the dashboard's poll to 15 to 30 s. Before the public launch (engine PR 10), verify the Neon plan's compute ceiling and load-test `/changes` at launch-scale concurrency.

- **[major] observability**: One process watches itself. `notify_operator` runs inside the engine process (§How an alert goes out, "Inside the engine"; Engine §H "Operator messages") and sends over Telegram, the same channel as the alerts. Some failures therefore produce silence instead of an alarm: an event loop blocked by a synchronous outlet call, a crash loop, a stuck advisory lock, or a Telegram outage. "A destination that is down holds up only itself" (§How an alert goes out) is true for I/O errors only, not for a sync SDK call or an unhandled exception in an outlet task sharing the loop with the feed pollers and price streams. For a product sold on "called in minutes", a silent stall is the worst failure, and nothing in any plan catches it.
  - **Recommendation:** In N1: (1) Add a $0 external dead-man's switch. The engine pings a heartbeat URL every minute, or a free uptime monitor polls the health endpoint, and the monitor emails Chris, so the alarm does not depend on Telegram or the engine. Verify a free provider before N1. (2) Outlets use async HTTP with hard per-call timeouts. No sync SDKs (for example tweepy's sync client or requests-based Pushover libraries). (3) Each worker catches and records its own exceptions. (4) Report event-loop lag in `engine status`. (5) Raise an operator notice for any `deliveries` row left in `sending` for more than 60 s, because at-most-once otherwise drops a public call silently.

- **[major] architecture**: One public API is split across two plans, and the split puts a cross-plan dependency on the cutover's critical path. N2 (alerts endpoints, schema, agent guide, `/status/outlets`) and D1 (signals, bars, evidence, track-record, `/status/engine`) build the same `/api/v1` app in parallel. D1 "waits on ... notification N2" and the cutover waits on D1 (Dashboard §Build order). The conventions both need have no named owner: the stream_id envelope, paging, real-client-IP rate limiting (today `api/rate_limit.py` keys on `get_ipaddr`, which resolves to Railway's proxy, per notes/notification-plan.md), the derived-numbers projection and the error shape. There are also two status endpoints for one status page.
  - **Recommendation:** Give `/api/v1` one owner. Move N2's endpoints, schema and `agents.md` into the dashboard plan's D1, or make N2 the API skeleton that merges first and D1 adds routes to it. Merge `/status/outlets` into a single `/api/v1/status`. The notification plan then shrinks to push delivery and operator notices. Decide this after engine PR 6, before either PR is written.

## Gaps

- **[major] scope**: The message people actually read is never designed. The plan specifies delivery semantics in detail (bookmarks, at-most/at-least-once, give-up age, signing). It never says what a Telegram alert, a result or an X post contains: the evidence line, tier, how confidence is worded, the derived move, "not investment advice", the link to `/s/<id>`, and the pre-PR-10 state where "alerts say that evidence is still being built" (Engine §F). The mission asks for alerts that carry "what the signal says, how it has performed historically, and how confident to be". The growth loop depends on a post that reads well when forwarded (Growth §How people find us). For followers, the message is the product. The plan spends its detail on agent plumbing.
  - **Recommendation:** N1 ships a small fixed template set with snapshot tests: pre-evidence alert, evidence alert per tier, stock vs crypto, market-closed wording, operator notice. The result reply comes later with PR 10. Each template uses only `alert.v1` derived fields. Chris approves sample renders before the shadow week, and the shadow week reviews wording as Growth §Launch step 2 intends.

- **[minor] scope**: Cut `audience_daily` and named-invite-link attribution code. Growth asks this plan to "give each outlet a named Telegram invite link and keep a daily audience count it owns". Per-link join attribution through the Bot API needs `chat_member` updates, which means an inbound bot path. The plan deletes the only one (`api/routers/telegram.py`, §What we don't keep). People who join a public channel through its @username are not attributed to any link anyway. The number only feeds the 2,000-follower gate check, which is read rarely.
  - **Recommendation:** Chris creates the named invite links by hand and reads joins per link in Telegram's admin view. Verify that this view exists before dropping the code. At most, log `getChatMemberCount` in the engine's daily status line. No table, no job, no inbound updates. Remove the item from the growth change list for Notifications and from the app schema (Engine §H "App schema").

## Questions

- **[minor] scope**: Do the two X gates collapse into one? The public launch itself requires "an edge after costs" in the backtest report (Growth §Launch step 4), and N5's per-alert posting waits for the same thing: "N5 also waits for the backtest to show an edge after costs" (§Build, Gates). So "X at launch for the report, results and scorecard; per-alert posts still wait for an edge" is either one gate, in which case ship one N5 at launch, or the per-alert gate means the live-record edge (Growth paid gate check 2), in which case the plan should say so. If X's pay-per-use price or free tier does not check out (unverified, §Costs), is the fallback no X automation, with Chris posting the report thread and scorecard by hand? Verify X API pricing before N5 is written.

- **[minor] data-integrity**: What does the 30-minute give-up age measure, and what does it apply to? Is it post time, first-seen or alert creation (§How an alert goes out, "Give-up age")? Measured from the alert, every result update (days later) would be skipped. Measured from the revision, a skipped alert's later updates need their own rule ("along with its updates"). When the channel skips an alert the engine marked "sent", does `/record` count it as "called in public" (Growth: "every call made in public within minutes")? Staleness is a property of the call. Should the engine decide it once, on the alert, so the outlets and the public record cannot disagree?

## Observations

- **[info] scope**: Restated problem, without the solution: get each market call, with its evidence and how far to trust it, in front of the people who might act on it while it is still actionable. Then show them, in a way they can verify, whether it was right, at near-zero cost, never stale, duplicated or altered, and in a form that grows a following. What I would build from scratch: one outbox follower inside the engine that posts each call once to a Telegram channel, never edited, replies once with the headline result, and alarms the operator out-of-band. A public read API whose change feed is cached so its cost is flat in audience size. X once there is something worth posting per call. The plan's core (insert-only revisions, a global seq, one bookmark per outlet) matches that and is sound. Where it diverges is breadth: webhooks, keys, MCP, phone push, per-destination delays and audience tables all come before any consumer or edge exists.

- **[info] scope**: Cut or defer the optional outlets. N6 (Pushover, $5 plus a new vendor, key and adapter) is a second Telegram destination: a private chat with the bot, filtered to HIGH, with its own notification sound set in Telegram. That is $0 and no new code beyond a bookmark row. N4 (MCP plus Registry listing) is cheap but serves a hypothetical audience. REST plus the JSON Schema plus `agents.md` already serve agents. Build it after the public launch, once API logs show third-party, non-dashboard clients, and keep it out of the launch-critical set.
