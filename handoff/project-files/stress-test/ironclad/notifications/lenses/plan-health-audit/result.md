## Blockers

- **[critical] compatibility**: The `alert.v1` content contract is not settled, and N2 publishes and freezes it. (Hookup to the engine, "Updates" and "Alerts"; For agents; N2 row.) Four plans disagree about what is in it:
  - The notification doc and the engine plan (workstream F, table H "Alert updates") say the first result "carries the entry price and time used". The growth plan, and the engine's own Data model section, say no raw entry price goes out publicly, because a % series plus one price rebuilds the raw prices and Alpaca's free plan bars public display. `/api/v1/alerts`, `/mcp`, webhooks, Telegram, X and the published JSON Schema are all public or redistributed.
  - The doc's filter has "tradeable now". The engine has two different fields, `tradeable` (edge survives costs) and `market_open` (market could be traded when the alert went out). A builder has to guess which one.
  - Growth wants "each alert's public post links" in the alerts API. Those message ids exist only in `deliveries` (app schema) and appear after the revision is written. They cannot sit in an insert-only revision, and the cursor does not move when a link appears.
  - The engine's newer fields (`public_id`, per-instrument `asset_class` / `symbol` / `slug`, `market_open`) are not in this doc, and the doc says "new fields are optional... a breaking change becomes alert.v2". If N2 ships `entry_price` and it is later removed, that costs a v2.
  - It is also unclear who owns the schema. The engine says `alerts` holds alert.v1 (PR 6). This plan writes `/api/v1/schema/alert.v1.json` (N2). Neither plan names the model the schema is generated from.
  - **Recommendation:** Do not write N2 until one field list exists. Engine PR 6 owns the `AlertV1` model, and N2 serves the JSON Schema generated from it, with a contract test that fails on drift. Strike entry price from alert.v1 (keep it in `alert_progress` and the engine's internal tables). Rename the filter to `tradeable` and `market_open` explicitly. Attach public post links by a read-time join in N2 and say they can lag the alert by seconds. Add `public_id`. Record each of these as a dated agreement between the engine and notification planners.

- **[critical] architecture**: The doc's cursor is the old one. Its change cursor is `alerts.seq` (Hookup, "Alerts": "a revision and a seq number taken from one running count on every save"; How an alert goes out; For agents "Pull": `/changes` "returns every alert created or changed since that number, each whole"). The engine plan (rev 130) and the planner notes agreed `alert_revisions.seq`: insert-only rows, several per alert, a stream id on every cursor reply, and delayed readers taking revisions older than their delay. A builder following this doc would build the wrong thing:
  - N1's bookmark and `deliveries` key on an alert-level seq, so a delayed destination (growth's paid-first design) sees the already-updated alert and cannot publish the first call.
  - N2's `/changes` returns one row per alert instead of one row per revision. The dashboard plan's agreement is that the client keeps the highest revision per alert_id.
  - `engine_meta.stream_id` appears nowhere in this doc. Bookmarks and webhook "start after" numbers have no way to notice a replaced database. "Replaying is moving a bookmark back" is only true within one stream.
  - "A reader that missed a change gets the alert as it stands, which already holds every earlier result" is true under the old cursor and not under the new one.
  - N2's "exactly once, in order" test is undefined (per alert or per revision).
  - **Recommendation:** Rewrite How an alert goes out, Hookup "Alerts", the N1, N2 and N3 rows and the For agents "Pull" text on `alert_revisions(seq, alert_id, revision, payload, created_at)`. `/changes` returns revisions and every response carries `stream_id`. Add a stream-id mismatch case (bookmark resets) to the N1 and N2 tests. Settle in one sentence whether a collapsed "latest only" read exists. Recommend no.
