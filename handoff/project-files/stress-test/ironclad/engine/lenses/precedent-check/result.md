## Risks

- **[major] scope**: The data model repeats the pattern this repo has deleted most often, schema and abstractions built for sources and outlets that never arrived. Precedents: (1) `signals` was designed "source-agnostic" in Feb 2026 and was "100% write-only" for weeks (`documentation/planning/SIGNALS_MIGRATION.md:9`, `:289`). The dual-write cutover then took until PR #140 (merged 2026-04-19) and is still unfinished (#224 open, #254). (2) `HarvesterRegistry` plus a `TwitterHarvester` skeleton came from a 70 KB plan (`documentation/archive/system-evolution_2026-02-11/06_harvester-abstraction-layer.md`), have zero callers, and are slated for deletion (`documentation/planning/dead-code-cleanup_2026-07-24/06_finish-signals-migration.md:57`, #224 M24). (3) The `subscribers` and `llm_feedback` tables were dropped with zero code references (`scripts/006_drop_dead_tables.sql`, c1264f2). (4) The Kafka/Redis addendum justified an event backbone by a projected 800-6,000 events/day across 5-10 sources (`ARCHITECTURE_EVALUATION_ADDENDUM_KAFKA.md:48`). The reality is one source at about 13 text posts/day (21,862 posts since Feb 2022, `/mnt/project-files/research/post-timing/README.md`). (5) An email/SMS dispatcher was built and never wired (M20); Telegram is the only live channel. The engine plan has about 26 tables (24 in its Data model table, plus `job_runs` and `engine_meta`) against about 13 in the old system. It creates the app schema in PR 1 (hookup row "App schema") although those tables' readers arrive with N1 (after PR 6) and D1 (after PR 8). It also builds the "new source is a row and an adapter" machinery in PR 2 while saying the second source waits for PR 12 and an edge.
  - **Recommendation:** Adopt a rule in the plan: no table, column or adapter lands before the PR whose code reads it. Make PR 1 create only the two schemas, the roles and the migration mechanism; the app tables arrive with N1 and D1, written by their owners. Defer until a reader exists: `slug_redirects`, `alert_progress`, `latest_prices`, display-rights enforcement in `price_sources`, `audience_daily`, and the stream-id and delayed-reader cursor features (until a second outlet exists). Keep `signal_sightings`, because feed lag is this plan's own core measurement. Treat "add a source" as a PR 12 task, not PR 2 infrastructure.

- **[major] architecture**: "Stage stored in Postgres, nothing to claim or reclaim" (workstream A) replaces the event queue without saying how it avoids that queue's three documented failures. (a) C4/#201: a crash between claim and process wedged events forever (`shit/events/worker.py:141-224`). (b) H5/#207: a failed LLM call leaves no DB footprint, so the signal is retried forever with repeated spend (`shitpost_ai/shitpost_analyzer.py:539-541`). (c) C3/C5/#202: two executors double-spend and double-send. The new design has the same exposure. A signal that raises (not times out) in extraction stays in its stage and is retried on every restart. The repo's restart policy is `ON_FAILURE` with 10 retries (`railway.json:16-17`), so a poison post can leave the only process permanently stopped. Railway's zero-downtime deploys can run old and new engine instances side by side (the overlap setting needs verifying), which gives two pollers, double model spend per post and two Alembic runs at start-up. The plan specifies insert-only and ordering guarantees for `alert_revisions` but no uniqueness of one alert per signal. The migration story also has a cross-service gap, and it is the 008 failure shape. `scripts/008_schema_cleanup.sql:25-26` dropped `market_volatility` and `notes` while the model still declares them (`shit/market_data/models.py:154,160`), so maturation fails daily. In the new plan the web service deploys separately and reads engine tables whose DDL runs inside engine start-up, and other plans' app-schema DDL also rides the engine's history.
  - **Recommendation:** (1) Take a Postgres advisory-lock singleton at start-up (a second instance idles or exits), covering the Alembic run too. (2) Give `signals` an `attempts` count, a `last_error`, and a terminal `error` stage that parks a signal after N failures and notifies. (3) Add UNIQUE(`alerts.signal_id`) and UNIQUE(`extractions.signal_id`, method, version). (4) Make PR 6's acceptance tests include kill -9 mid-extract, two concurrent engines, and a poison post. (5) Set the engine's restart policy to always-restart. (6) Adopt an expand/contract rule (no drop or rename while any other service's deployed code reads it), plus a CI job that runs the web app's and dashboard's queries against the head schema.

- **[major] observability**: Four failures ran for months and were found by audits, not alarms. Outcome maturation has failed daily since 31 Jul (the 008 drift above). Snapshot capture silently captured 0 (85a2664, #121, "prevents silent pipeline failures from going undetected"). The morning briefing was dark every winter weekday, Nov-Mar (b1bf662, #230 L3). Production alerts had hardcoded neutral sentiment and empty thesis since April (#198, still open). Moving from crons to one process also loses Railway's per-run success tracking, which the old architecture relied on (`documentation/archive/ARCHITECTURE_EVALUATION.md` section 10.7). The plan's watchdog (`feed_health`, `job_runs`, "admin message after two failures") lives inside the process it watches and sends through N1's `notify_operator`, which "until N1 lands, logs". A dead process, a stuck event loop or a revoked Telegram token is therefore silent, and the shadow week starts before N1 has proven itself.
  - **Recommendation:** Add an external dead-man's switch in PR 1, not PR 7. Point a free uptime monitor at the health endpoint, which returns non-200 on a stale feed, no poll in 3 minutes, a job_run past due, or no heartbeat. Send a daily heartbeat to the admin chat (posts seen, alerts sent, jobs ok) so silence is the alarm. Run the scheduler in a named time zone and test it across the March and November transitions (the b1bf662 bug).

- **[major] data-integrity**: Ticker extraction was the old system's biggest data-quality drain. 377 of 2,694 completed predictions (14%) carried at least one bad ticker: delisted (RTN, TWTR, FB), concepts (DEFENSE, CRYPTO) and foreign symbols (`documentation/planning/investigations/ticker-validation_2026-04-09/00_INVESTIGATION.md:21`, PR #132, 00dcaa0). Ordinary words that collide with real tickers then needed a hand blocklist: GOLD, STEEL, COAL, TAX, WIN, WAR, JOBS, NEWS (5bdf84b, `shit/market_data/ticker_validator.py:33`). Three conflicting validity rules still exist (#252). The plan's single rule, "a US-listed stock or ETF with bars on the post date, or a coin Alpaca covers" (workstream C), accepts every collision, because they are real tickers with bars. "Bars on the post date" catches delisted names, not word collisions. This matters three times over. Keyword rules (company names, tickers, topic words) are the baseline an edge must beat, the fallback alert path on a model timeout, and the only evidence layer over all history. A polluted keyword layer produces a false edge or hides a real one.
  - **Recommendation:** Carry the collision list over as data (an `instrument_aliases` kind such as `collision`). Require a cashtag or a full company name for any ambiguous symbol (short, English-word tickers). Add an acceptance step to PR 4: hand-label about 200 keyword hits spread across years and publish precision per rule. Do not send alerts from `fallback`-marked extractions until that precision is known.

- **[major] scope**: The gate ordering repeats April 2026. Nine of the twelve brainstormed features (fundamentals, watchlist, echoes, ensemble, calibration, briefing, follow-ups, voting, scorecard) were built and merged in about 3 days (PRs #133-#139, 2026-04-10 to 04-12). Merges came from 15 seconds to 10 minutes after opening. The three latency and alert-volume items stayed at "Planning": always-on harvester, smart batching, push (`documentation/planning/product-brainstorm_2026-04-09/00_OVERVIEW.md:88`, `01_ALWAYS_ON_HARVESTER.md:5`). Nobody measured whether any call had edge. The repo map records no baseline, benchmark or significance test anywhere (`/mnt/project-files/discovery/repo-map.md`). The only "backtest" was an equity curve summing raw `pnl_t7` at confidence 0.75 or higher, deleted with the Dash UI (a537bc4, `shitty_ui/data/backtest_queries.py`). Meanwhile live alerts were degraded (#198). The engine plan's order is build (PRs 1-6), shadow (7), move subscribers (8), and only then the evidence gate (PR 10, "until PR 10, alerts say that evidence is still being built"). That is the same ordering: subscribers move to the new alert path before there is evidence it deserves alerts, and the "stop and rethink" gate sits after the Railway spend, the shadow week and the subscriber carry-over message.
  - **Recommendation:** Move the go/no-go earlier. PR 5 produces the keyword-only report in the sandbox at no spend. Make Chris's read of it an explicit gate before PR 7 (Railway spend) and PR 8 (subscribers), with a decision rule agreed in advance. For example: no edge after costs on any topic or window means the engine runs as a measured-latency research service and old subscribers are not carried over. If Chris cuts over regardless, label the PR 8 alerts "experimental, no evidence" and defer the subscriber carry-over until PR 10.

## Gaps

- **[major] data-integrity**: PR 9's "live record" layer (predictions production made in real time) imports a table with known contamination, and the plan lists only one filter (post time from signals). Known defects: (a) the 14% bad-ticker rate above; (b) junk predictions on parse failure, invented assets from words containing "inc" or "corp" with confidence 0.5, stored as completed (`shit/llm/llm_client.py:238-259`, #218); (c) the ensemble drops the custom prompt (#217, H15) and was introduced mid-history (#138, 2026-04-12), so `llm_model` and ensemble eras must not be pooled; (d) duplicates and retries (H5, H6); (e) the outcome anchor mismatch and first-sentiment fallback (M3, M4); (f) old-pipeline latency of up to about 20 minutes means "when the alert would have gone out" differs from the engine's.
  - **Recommendation:** Specify the inclusion filter in PR 9 and report excluded counts by reason. Keep only `analysis_status='completed'`, one row per signal, no parse-fallback rows (confidence exactly 0.5 with the junk-asset pattern), and tickers re-run through the new instrument rule. Partition by `llm_model` and ensemble flag, and take entry from `predictions.created_at` flagged as old-latency. If the filtered live record is under about 200 rows, say so and weight that layer accordingly.

- **[minor] scope**: There is no burst policy anywhere (engine or notification plan). The old brainstorm called burst alert fatigue "the #1 user experience problem" (3-8 posts in 15-30 minutes, causing mutes and unsubscribes; `product-brainstorm_2026-04-09/09_SMART_ALERT_BATCHING.md:11,21`) and never built it. The mission now adds users and followers as a goal. The new engine will fire one alert per post at 4-minute latency, each with LOW-tier evidence. The `sent`/`fyi`/`suppressed` disposition exists but has no rule. The backtest treats same-day posts as non-independent, but alerts do not.
  - **Recommendation:** Measure burst frequency from the CNN archive in PR 2 (posts within 30 minutes of the previous one). Put a minimal rule in PR 6's disposition logic: a second alert on the same instrument within N minutes becomes `fyi` or a revision of the first. Do not build a batching service.

- **[minor] dependencies**: Fallback chains have a record of being built and never exercised. `AlphaVantageProvider`, `ProviderChain` and the health module (about 600 lines, 9 settings, CHANGELOG.md:589; `shit/market_data/alphavantage_provider.py`, `health.py`, `price_provider.py`) shipped with `ALPHA_VANTAGE_API_KEY` defaulting to None (`shit/config/shitpost_settings.py:92`), so the fallback is inert unless someone set it, and nothing in the repo shows it ever fired. PR 3 builds three adapters (Alpaca, yfinance, Coinbase) plus crypto bars, a BTC benchmark and a second stream while Chris's crypto card is still open and neither Alpaca nor Coinbase is reachable from the sandbox, so they can be tested from recordings only. Fallback yfinance data also differs in kind: no IEX or consolidated flag, 5-minute bars for 60 days only. A silent failover would change backtest semantics.
  - **Recommendation:** Build the price-source interface plus the Alpaca adapter in PR 3. Keep yfinance as a research and cross-check source only (it is the one reachable now), and cut the Coinbase adapter until Alpaca crypto actually fails on Railway. Gate crypto work behind its approval card. Make any failover flip a visible feed-health state and not a silent swap.
